# Product Decisions — 6 August 2026

**Зафиксировано:** 2026-08-06T16:32:49+04:00

## 1. Общая продуктовая цель

Workspace не является копией LibreOffice, Microsoft
Office или другого существующего пакета.

Ценность Workspace — в связи между рабочими объектами,
действиями и инструментами внутри одной локальной
системы.

Пользователь должен иметь возможность:

- создать проект;
- определить задачу;
- открыть исходный материал;
- вызвать подходящий инструмент;
- сохранить результат;
- вернуться к результату из проекта и задачи.

Первая версия не должна состоять из декоративных карточек
и обещаний, что настоящие возможности появятся позже.

Нужны небольшие, но законченные сквозные маршруты.

## 2. Фундаментальные модули

Фундаментальный модуль владеет рабочими объектами и их
жизненным циклом.

К фундаментальным направлениям относятся:

- Files;
- Projects;
- Office;
- Notes;
- Tasks;
- Web Studio;
- Chat.

Раздел Tools является каноническим каталогом
прикладных инструментов.

## 3. Встраиваемые инструменты

Инструмент создаётся один раз и может запускаться из
разных рабочих контекстов.

Примеры:

- Files открывает конвертер изображений;
- Office открывает таблицу или формулу;
- Tasks запускает инструмент для выполнения задачи;
- Web Studio открывает обработку изображения;
- Projects открывает просмотр или обработку данных.

Модуль владеет объектом.

Инструмент выполняет операцию или редактирование и
возвращает результат владельцу.

Не создавать:

- отдельные копии одного инструмента для разных модулей;
- скрытые хранилища внутри каждого инструмента;
- несовместимые варианты одного рабочего объекта.

## 4. Tools и Workshop — разные слои

`Tools`:

- содержит готовые прикладные возможности;
- используется непосредственно в работе;
- может открываться из разных модулей.

`Workshop`:

- относится к Web Studio;
- является авторской средой пакетов;
- работает с шаблонами, темами, блоками, виджетами,
  ассетами и стартовыми наборами;
- управляет версиями, совместимостью и проверкой пакетов.

Мастерская не переносится в раздел Tools.

## 5. Web Studio и Workshop

Кнопка `Шаблоны / Templates` остаётся прямой кнопкой
верхней шапки Web Studio.

Она не переносится в выпадающее меню и не скрывается.

Новая прямая кнопка:

`Мастерская / Workshop`

должна находиться сразу после `Шаблоны / Templates`.

Принятый порядок:

`Сайты → Настройки → Шаблоны → Мастерская → Редактор
→ Страницы → Меню → Дизайн → Предпросмотр → Сервер
→ Опубликовать`

При открытии Мастерской меняется только центральная
рабочая страница Web Studio.

Не меняются:

- браузерная оболочка Workspace;
- логотип;
- адресная и верхняя браузерная панель;
- общая шапка Web Studio.

Сохраняются:

- технический route `codehub`;
- существующий CodeHub store;
- функциональность восстановленной Мастерской;
- полноформатная рабочая поверхность.

Встроенной Мастерской не нужна дублирующая навигация
всего Workspace.

## 6. Шаблоны и Мастерская

Шаблоны — пользовательская витрина готовых пакетов.

Мастерская — авторская среда создания и проверки пакетов.

Сквозная цепочка:

`Мастерская создаёт и проверяет пакет
→ Шаблоны показывают пакет
→ Web Studio применяет пакет к сайту`

## 7. Главная Workspace

Внешние карточки `Шаблоны` и `Мастерская` после
интеграции с Web Studio должны быть переосмыслены в
текущей версии.

Не заменять освободившиеся места случайными новыми
модулями.

Сначала должна быть принята продуктовая карта и
спецификация главной страницы.

Главная не обязана зеркально повторять всё меню.

Она должна помогать продолжить реальную работу.

## 8. Tasks

Tasks не должен быть обычным todo-листом.

Он должен связывать:

`проект → источник → действие или инструмент
→ один или несколько результатов`

Задача должна позволять:

- открыть источник;
- открыть нужный модуль;
- запустить подходящий инструмент;
- создать результат;
- привязать существующий результат;
- вернуться к результату;
- завершить или вернуть задачу в работу.

Технический route `analytics` пока сохраняется.

Видимое направление:

`Задачи / Tasks`

## 9. Web Studio

Нельзя заранее считать Web Studio недоделанной по старым
спискам.

Многие функции уже реализованы.

Перед новыми требованиями необходимо провести
фактическую инвентаризацию текущего состояния.

## 10. Порядок дальнейшей работы

1. Принять продуктовую карту.
2. Провести фактическую инвентаризацию возможностей.
3. Принять контракт встраиваемых инструментов.
4. Принять спецификацию интеграции Мастерской.
5. Принять спецификацию главной.
6. Подготовить полный пакет Tasks v1.
7. После этого переходить к коду.
